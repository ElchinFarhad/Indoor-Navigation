# Supermarket navigation: requirements and logic

Can the QR-based indoor navigation be used in a supermarket? Yes. The positioning (one QR scan, then
motion sensors matched to the walkable graph), the routing, the AR arrows, the map and the voice carry
over unchanged: aisles are corridors, shelf sections are destinations. What a supermarket adds is that
people do not go to *one* place: they have a **shopping list**, and want the shortest way past
everything on it, ending at the checkout.

This document states the requirements, what is implemented on this branch, and what a real deployment
would still need.

## 1. Requirements

### Shopper

| # | Requirement | Status |
|---|---|---|
| S1 | Find a product by name and see which section it is in | done |
| S2 | Keep a shopping list on the phone (add, remove, clear; survives closing the page) | done |
| S3 | See before starting how many stops the list means and roughly how far the walk is | done |
| S4 | Be guided through all products in the shortest walking order, not in the order written | done |
| S5 | Products on the same shelf are one stop; the stop lists what to pick up there | done |
| S6 | One QR scan at the start; no scanning at every shelf | done |
| S7 | At each stop: which side the shelf is on, what to take, one tap to continue | done |
| S8 | The trip ends at the checkout | done |
| S9 | Starting somewhere else than the entrance re-plans the order from there | done |
| S10 | Go to a single section without a list (as in any building) | done |
| S11 | Spoken guidance between stops ("Next: bread, at Bakery") | done |
| S12 | Skip a product that is out of stock, add one on the way | not yet |
| S13 | Exact shelf position (bay, height) and price of a product | not yet (needs store data) |

### Store operator

| # | Requirement | Status |
|---|---|---|
| O1 | Few markers: floor stickers at the aisle ends and the entrance, not at every shelf | done (14 for 38 graph points) |
| O2 | Layout and assortment as data, no code: sections, aisles, products per section | done (`supermarket.json`) |
| O3 | No app install, no beacons, no Wi-Fi fingerprinting, no account | done |
| O4 | Nothing about the shopper leaves the phone (no tracking) | done |
| O5 | Several venues in one installation | done (`venues.ts`, `?venue=` link) |
| O6 | Assortment kept current from the store's product system (planogram / ERP feed) | not yet: the catalogue is a static file |
| O7 | Promotions, stock, prices | out of scope here |

## 2. Data model

A venue is one JSON file (`react-client/src/db/supermarket.json`) in the format of the building graph,
with `meta.type: "store"` and a `products` list:

```jsonc
{
  "meta": { "name": "FreshMart Supermarket", "type": "store", "metersPerUnit": 0.1, "floors": [{
    "rooms": [{
      "id": "milk", "name": "Milk & yoghurt", "kind": "dairy",
      "solid": true,                       // a shelf: a block, not a room one walks into
      "x": 400, "y": 60, "w": 20, "h": 75,
      "doors": [{ "x": 400, "y": 105 }],   // the point of its face the shopper stands in front of
      "node": 34                           // the stop in the aisle
    }]
  }] },
  "nodes": [
    { "id": 34, "type": "room", "label": "Milk & yoghurt", "room": "milk", "qr": false, "x": 370, "y": 105, "path": [] }
  ],
  "products": [{ "id": "milk", "name": "Milk", "section": "milk" }]
}
```

- **Sections** are the shelves and counters. Each has one stop: a graph node in the aisle in front of it.
  The two shelves facing each other across an aisle have their own stops, slightly staggered, so the app
  can say "on your left" or "on your right".
- **Markers** exist only where `qr` is not `false`: both ends of every aisle, the entrance, the checkout.
- **Products** point at a section. Several products can share one.

The demo store (42 m x 30 m, six aisles, 29 sections, 93 products) is generated by
`react-client/scripts/build-supermarket.js`. It is a designed layout, not a real shop.

## 3. Logic

### Planning the trip (`src/nav/shopping.ts`)

1. Look every list entry up in the catalogue; unknown ones are reported, duplicates ignored.
2. Group the products by the stop of their section.
3. Order the stops so that the walk *start -> every stop -> checkout* is as short as possible. Distances
   are walking distances through the aisles (Dijkstra), not straight lines.
   - Up to 12 stops: exact, by dynamic programming over subsets of stops (Held-Karp), a few
     milliseconds on a phone.
   - More than 12: nearest neighbour followed by 2-opt improvement.
4. Append the checkout.

The start is the entrance, or the marker the shopper is known to be at. The unit tests compare the
result with a brute-force search over every possible order.

### Walking the trip (`components/QrScanner.tsx`, route `/shop?items=milk,bread`)

- The navigation session always navigates to the *current stop*; everything else (tracking, re-routing,
  arrows, map, voice) is the single-destination machinery.
- First scan somewhere other than the planned start: the trip is planned again from there, and if the
  first stop changes the app says so.
- Arriving at a stop shows what to pick up there and on which side the shelf is. "Got it, next stop"
  moves the session to the next stop and announces it.
- The last stop is the checkout; finishing clears the list.

### Positioning in a store

Unchanged, with one difference in deployment: markers are sparse. Between two aisle-end markers the
position comes from step counting matched to the aisle, and every turn into or out of an aisle snaps the
estimate onto the aisle end. An aisle is at most about 20 m, so the error stays small; and any marker
that comes into the camera's view corrects it.

## 4. What a real store would still need

- **The real layout and assortment.** Trace the store's plan and connect the catalogue to the store's
  own data (which product is in which section changes weekly). That needs an import step or a small
  backend, which this project deliberately does not have.
- **Finer product positions.** A section here is 7.5 m of shelf. A planogram would give the bay.
- **Field tuning.** As for the building: step detection, step length and camera field of view were not
  measured on a phone. A supermarket adds trolleys (a phone on a trolley handle bounces differently from
  one in the hand, so the step detector will need a profile for it), crowded aisles and reflective floors.
- **Open areas.** Fresh produce is often an open space rather than an aisle; the graph can model it with
  a few more nodes, but tracking in open areas is weaker than in aisles.
- **Operations.** Markers wear out on a shop floor; a wall or shelf-end mounting (supported by the data
  model as `"mount": "wall"`) may last longer.

## 5. Try it

```bash
cd react-client
npm start
```

Open `http://localhost:3000/?venue=supermarket` (or choose the store in the top bar), add a few products,
*Start shopping*, then *Try a simulated walk*.
